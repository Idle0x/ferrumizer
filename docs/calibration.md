# Calibration

Ferrumizer calibrates the process parameters
`{log D0, Q, C_pot, h_m, ε}` against a measured hardness traverse using
NumPyro NUTS. The result is a **posterior**, not a point estimate: for each
parameter you get a mean, a credible interval, and convergence diagnostics
(R̂, bulk ESS).

The forward model used inside the likelihood is the **lumped-capacitance
thermal surrogate** (see [ADR-002](adr/ADR-002-calibration-surrogate.md)),
which is V1-validated to < 0.5% error against the full PDE path while keeping
each likelihood evaluation tractable (~1.5 s at the shipped grid). The full
PDE path remains available for forward simulation, figures, and verification.

## Boundary condition: mass-transfer (Robin), never Dirichlet

Calibration **always uses the mass-transfer (Robin) carbon boundary condition**
(`carbon_mode="mass_transfer"`). The likelihood samples `h_m` (the
mass-transfer coefficient), which **has no effect under a Dirichlet boundary**
— where the surface concentration is pinned at `C_pot`, `h_m` does not appear
in the governing equation. Sampling a dead parameter wastes effective sample
size on a flat direction and can destabilize the other parameters; the
calibration entry point therefore **raises an error** if asked to run in
Dirichlet mode.

The data config generated by `make data`
([`data/synthetic/calibration_data.yaml`](../data/synthetic/calibration_data.yaml))
is coherent with this: it declares `mode: mass_transfer`, the two traverses at
900 °C and 1000 °C, and both schedules.

## The identifiability rule (read this first)

A single temperature schedule leaves **D₀ and Q statistically tangled**
(Arrhenius compensation: a higher prefactor with a higher activation energy
predicts nearly the same diffusivity). Figure F8 shows the correlation
structure; the consequence is that a one-schedule calibration reports a wide,
flat joint posterior over the pair even when the data is clean.

**The prescribed protocol is two furnace schedules at different temperatures**
(see `ferrumize identifiability` and [F8](../README.md#f8--identifiability-why-two-schedules-beat-one)).
Run two cycles, measure two traverses, and calibrate against both. The
calibration model accepts a second (depths, hardness, schedule) triple and
requires the **same parameters to explain both traverses** — that joint
constraint is what collapses the D0-Q ridge. The generated demo config ships
both schedules (`schedule` + `schedule2`, `traverse_csv` +
`traverse_csv2`).

Beyond the local Fisher analysis, `ferrumize identifiability` writes
**2-D profile likelihood contours** over (log D0, Q) for the single and
two-schedule cases: a flat ridge in the single-schedule panel and a tight
well in the two-schedule panel is the global, non-Gaussian proof that the
protocol works.

## Workflow

```bash
# 1. Prepare a traverse (depth_mm, hardness_HV), surface first
#    — or ingest it from a raw furnace log:
ferrumize ingest /path/to/plc_export.log --out results/ingested

# 2. Run the calibration (two-schedule protocol when the config has schedule2)
ferrumize calibrate data/synthetic/calibration_data.yaml --chains 2 --draws 300

# 3. Check the gate verdict
#    R-hat < 1.01 and bulk ESS > 400 for every parameter, else exit code 1.
#    A posterior predictive check plot (observed vs predicted hardness with
#    90% credible band) is written to ppc_hardness.png in the output dir.
```

The app's **Cycle Predictor** tab runs the same code with a light grid
(`carbon_n=41, dt=8 s`) and an upfront runtime warning — the light grid is
for interactivity, not for research-grade posteriors.

## Measurement noise: inferred, not assumed

Measurement scatter (HV) is **inferred hierarchically** by default
(`infer_sigma=True`): a `sigma_hv` parameter is sampled with a HalfNormal(15)
prior, so the posterior is not overconfident when the true measurement noise
is larger than the textbook repeatability value. Pass `infer_sigma=False`
with an explicit `sigma_hv` to fix it instead.

## Runtime expectations (CPU)

| Scenario | ~Wall time |
|---|---|
| Smoke (1 chain, 100/100) | 5–10 min |
| Credible (2 chains, 300/300, light grid) | 30–60 min |
| Full default (4 chains, 1000/1000, shipped grid) | hours |

Reduce the carbon grid (`carbon.n`, `carbon.dt`) in the config to trade
accuracy for speed; the prior corners are kept stable by adaptive
sub-stepping in the JAX twin.

## What the gates mean

- **R̂ (R-hat) < 1.01**: chains have mixed and agree; values above indicate
  the sampler has not converged.
- **bulk ESS > 400**: enough effectively-independent posterior samples for
  stable interval estimates.
- **Posterior predictive check (PPC)**: does the posterior actually reproduce
  the observed traverse? The PPC plot overlays observed hardness vs the
  posterior-mean prediction with a 90% credible band. Residual structure
  (bias, curvature) indicates model misspecification that convergence gates
  cannot catch.

A run that fails the gates exits non-zero and writes **no** posterior — the
gates are release gates, not warnings.

## Output

The posterior summary (per-parameter mean, sd, R̂, ESS, 90% HDI, gate
verdict), the marginal plots (figure F6), the posterior predictive check
plot (`ppc_hardness.png`), and the raw MCMC object are written under the
output directory. F6 is regenerated by
`ferrumize figures --only F6` after a calibration run.

See [verification.md](verification.md) for V6 (two-schedule recovery;
strongly-identified parameters to < 5e-3, h_m to a documented factor-2
tolerance) and V7 (SBC with N_SIM ≥ 200, prior-based initialization, honest
binomial coverage band).
